Что такое база данных — на пальцах

Ещё операторы для WHERE

  • IN — список: WHERE city IN ('Питер', 'Москва') — то же, что city='Питер' OR city='Москва'
  • BETWEEN — диапазон: WHERE amount BETWEEN 1000 AND 5000 (границы включаются)
  • LIKE — маска: WHERE name LIKE 'Б%' — имена на «Б» (% — любое число символов, _ — ровно один)
  • AS — переименовать столбец в результате: SELECT name AS cat_name
  • -- текст — комментарий, база его не выполняет
Кошка Селекта про NULL:
NULL — не ноль и не пустая строка, а «значения нет вообще». Как миска, в которую забыли насыпать корм: миска есть, корма — NULL. Сравнивать через = нельзя — только IS NULL / IS NOT NULL. Заменить NULL на что-то: COALESCE(fluff_level, 0) — «если пусто, считай нулём».

Глава 2. Порядок выполнения — почему база «не видит» твой алиас

Секрет, объясняющий половину «почему не работает»: база выполняет запрос НЕ в том порядке, в каком ты его пишешь.

ПорядокЧто делает
1. FROMберёт таблицы, делает JOIN
2. WHEREотсеивает строки
3. GROUP BYгруппирует
4. HAVINGотсеивает группы
5. SELECTвыбирает столбцы, считает
6. ORDER BYсортирует

Зачем это знать: алиас из SELECT нельзя использовать в WHERE — когда WHERE работает (шаг 2), алиаса ещё не существует (он родится на шаге 5). А в ORDER BY (шаг 6) — можно, он уже есть!
Глава 3. GROUP BY — сворачиваем строки в итоги

Вопрос: «сколько всего оплачено каждым котом?»

SELECT cat_id, SUM(amount) AS total, COUNT(*) AS cnt FROM orders WHERE status = 'paid' GROUP BY cat_id;
Было: оплаченные заказы (после WHERE)
cat_idamount
15000
27800
31200
Стало: одна строка на кота
cat_idtotalcnt
150001
278001
312001
Что произошло: строки разложились по кучкам (кучка = одинаковый cat_id), и по каждой кучке посчитались SUM и COUNT. Каждая кучка стала ОДНОЙ строкой результата. Детали внутри кучки исчезли — остались только итоги.

Функции-счётчики: COUNT(*) — сколько строк, COUNT(DISTINCT col) — сколько разных значений, SUM / AVG / MIN / MAX.

Правило GROUP BY: в SELECT можно писать только то, что есть в GROUP BY, или обёрнуто в функцию. Почему: после группировки «кучка» знает свой cat_id (он общий) и умеет считать итоги, но НЕ знает, какой конкретно amount показать — их там несколько! База честно отказывается угадывать и ругается.

HAVING — фильтр кучек

SELECT cat_id, SUM(amount) AS total FROM orders GROUP BY cat_id HAVING SUM(amount) > 5000;
Разница с WHERE: WHERE выкидывает СТРОКИ до группировки, HAVING выкидывает ГОТОВЫЕ КУЧКИ после. Здесь останется только кот 2 (7800) — у остальных итог меньше.

Глава 5. Даты и текст
-- вытащить месяц из даты (PostgreSQL) SELECT id, EXTRACT(MONTH FROM created_at) AS mon FROM orders; -- id=101 → mon=1, id=104 → mon=2 SELECT DATE_TRUNC('month', created_at) FROM orders; -- «обнуляет» дату до начала месяца: 2026-01-05 → 2026-01-01 -- текст SELECT UPPER(name) FROM cats; -- БАРСИК SELECT LENGTH(name) FROM cats; -- 6 SELECT CONCAT(name, ' из ', city) FROM cats; -- Барсик из Питер
Зачем это: в отчётах почти всегда группируют по месяцам — GROUP BY DATE_TRUNC('month', created_at) — это стандартный приём «продажи по месяцам».
Глава 6. JOIN — склеиваем две таблицы в одну

Проблема: в orders есть только cat_id (цифра), а имя кота лежит в другой таблице. JOIN приклеивает к каждой строке заказов данные её кота:

SELECT o.id, o.amount, c.name FROM orders o LEFT JOIN cats c ON o.cat_id = c.id;

Что произошло: для каждой строки orders база нашла в cats строку с таким же id (условие ON o.cat_id = c.id — «по какому столбцу склеивать») и дописала её столбцы справа. o и c — алиасы, короткие клички таблиц.

INNER vs LEFT — в чём разница

Добавим в cats кота Рыжика (id=4), у которого нет ни одного заказа, и склеим наоборот — от котов к заказам:

INNER JOIN: только пары
nameorder_id
Барсик101
Мурка103

Рыжика нет — пары не нашлось.

LEFT JOIN: ВСЕ из левой + пары
nameorder_id
Барсик101
Мурка103
РыжикNULL

Рыжик остался, заказа нет → NULL.

Когда что: LEFT JOIN — когда важно никого не потерять («покажи всех котов, даже безработных»). INNER — когда нужны только совпавшие. LEFT используется чаще. Кстати, «в результате стало БОЛЬШЕ строк, чем было» — это нормально: если у кота 2 заказа, его строка размножится на 2 (по строке на каждый заказ).
Выдра Куэри делится фактом:
У выдры есть любимый камень в кармашке под лапкой. У аналитика такой камень — LEFT JOIN: подходит почти для всего и всегда с собой. Три таблицы? Просто цепочка: второй JOIN приклеивается к результату первого.

Глава 8. Оконные функции — считаем итог, не убивая детали

Вспомни GROUP BY: он отвечает «сколько всего у каждого кота», но детали (отдельные заказы) исчезают. А что, если нужно И то И другое — каждый заказ + итог его кота рядом?

SELECT cat_id, amount, SUM(amount) OVER (PARTITION BY cat_id) AS cat_total FROM orders;
GROUP BY: 4 строки → 3, детали пропали
cat_idсумма
18200
27800
31200
Оконная: 4 строки → 4, итог дописан рядом
cat_idamountcat_total
150008200
132008200
278007800
312001200
Что произошло: ни одна строка не исчезла — у каждой просто появился новый столбец с итогом «её» группы. OVER = «поверх» строк, PARTITION BY cat_id = «окно — строки этого же кота». Зачем: теперь в одной строке есть и заказ (5000), и база для сравнения (8200) — можно посчитать долю 5000/8200 = 61%.

ROW_NUMBER — раздаём номерки внутри группы

SELECT cat_id, amount, ROW_NUMBER() OVER (PARTITION BY cat_id ORDER BY amount DESC) AS rn FROM orders;
Каждый кот получил свою нумерацию с 1
cat_idamountrn
150001
132002
278001
312001
Что произошло: внутри каждого «окна» (кота) строки выстроились по amount от большего к меньшему (ORDER BY внутри OVER) и получили номера 1, 2, 3... У следующего кота счёт начинается заново. Классика: «топ-1 заказ каждого кота» = оставить строки, где rn = 1. Родственники: RANK при равных значениях пропускает номер (1,2,2,4), DENSE_RANK — нет (1,2,2,3).

LAG — подглядываем в предыдущую строку

SELECT created_at, amount, LAG(amount) OVER (ORDER BY created_at) AS prev_amount FROM orders;
У каждой строки — значение предыдущей
created_atamountprev_amount
01-055000NULL

01-1078003200
02-0112007800
Что произошло: строки выстроились по дате, и каждая «заглянула» на строку выше. У первой предыдущей нет → NULL. Теперь легко посчитать «на сколько изменился заказ»: amount − prev_amount. LEAD — то же, но заглядывает вниз.

Нарастающий итог

SELECT created_at, amount, SUM(amount) OVER (ORDER BY created_at) AS running_total FROM orders;
Сумма накапливается сверху вниз
created_atamountrunning_total

Что произошло: когда внутри OVER есть ORDER BY, а PARTITION нет — окно каждой строки это «все строки от начала до меня». Поэтому сумма растёт с каждой строкой. Это «нарастающим итогом» из финансовых отчётов.
Чёрный кот Оконик подводит итог:
Запомни одной фразой: GROUP BY схлопывает строки в итоги, оконная функция дописывает итог рядом с каждой строкой. Как кот, который пересчитал все миски, но ни одну не тронул. Это спрашивают на каждом собеседовании — теперь ты готова.

Часть III

Power BI — рисуем данные красиво

Кошка Дашборда мурлычет:
Power BI — место, где твои данные надевают красивое и идут на встречу с руководством. Путь всегда один: подключил → почистил в Power Query → связал таблицы → написал меры DAX → собрал визуал. Идём по кликам.
Глава 1–2. Установка и подключение данных
Шаг 1. Скачай бесплатный Power BI Desktop (кнопка в «Песочницах» ниже). Только Windows.
Шаг 2. Слева три иконки: Отчёт (графики), Данные (таблицы), Модель (связи).
Шаг 3. Главная → Получить данные → «Книга Excel» или «Текст/CSV» → выбери файл → галочки на нужных листах.
Шаг 4. Нажми «Преобразовать данные» (НЕ «Загрузить»!) — попадёшь в Power Query.
Глава 3. Power Query — уборка данных
  • Типы данных: клик по иконке слева от имени столбца (123 / ABC / календарик) → правильный тип. Числа должны быть числами, даты — датами, иначе не посчитается!
  • Убрать строки: стрелка-фильтр на столбце → снять галочки (например, cancelled).
  • Merge (JOIN): Главная → Объединить запросы → вторая таблица + общий столбец. Это тот же LEFT JOIN из части I, только мышкой.
  • Append: Главная → Добавить запросы — склеить таблицы одну ПОД другой (данные за разные месяцы из разных файлов).

Все шаги пишутся справа в «Применённые шаги» — любой можно поправить. Закончила — «Закрыть и применить».

Глава 4. Связи между таблицами
Шаг 1. Окно Модель (третья иконка слева).
Шаг 2. Перетащи столбец cat_id из orders на id в cats. Появилась линия — связь готова.
Шаг 3. Проверь подписи на линии: «1» со стороны cats, «*» со стороны orders — один кот, много заказов.
Зачем связи: это тот же JOIN, но заданный один раз — теперь любой график сможет соединять «имя кота» и «сумму заказа» автоматически. Звёздная схема: в центре таблица фактов (orders — числа), вокруг измерения (cats, календарь), связи — лучами от центра.
Глава 5. Первый график — по кликам! 🎨
Шаг 1. Окно Отчёт. Справа две панели: Визуализации (иконки графиков) и Данные (твои таблицы с полями).
Шаг 2. Кликни иконку гистограммы (столбики) — на холсте появится пустая заготовка.
Шаг 3. В панели Данные раскрой cats и перетащи поле name в ячейку «Ось X» (под иконками визуалов).
Шаг 4. Раскрой orders и перетащи amount в «Ось Y». Power BI сам просуммирует — график готов: столбик на каждого кота!
Шаг 5. Добавь Срез (иконка воронки) → перетащи в него status → кликай «paid», и весь дашборд перестраивается. Это кросс-фильтрация.
Шаг 6. Кисточка «Формат» → цвета, подписи данных, заголовок. Не увлекайся: 2–3 цвета на весь дашборд.

Глава 6. DAX — формулы, которые думают
Кот Джойн объясняет на мисках:
Вычисляемый столбец — насыпал корм заранее во все миски: посчитан один раз, лежит в таблице. Мера — кот, который пересчитывает корм каждый раз при открытии шкафа: реагирует на фильтры и срезы. Кликнула «Питер» в срезе — мера пересчиталась только по питерским. Для сумм и средних почти всегда нужна мера!
Как создать меру: правый клик на таблице в панели Данные → «Создать меру» → формула в строку сверху → Enter. Мера появится в списке полей со значком калькулятора.
Общая сумма = SUM(orders[amount]) Сумма оплаченных = CALCULATE(SUM(orders[amount]), orders[status] = "paid") Продажи год назад = CALCULATE([Общая сумма], SAMEPERIODLASTYEAR(dates[Date]))
Про CALCULATE: это королева DAX — она меняет условия, при которых считается формула. «Посчитай сумму, но только по оплаченным» — независимо от того, что выбрано на дашборде. Для сравнения периодов (год к году) нужна отдельная таблица дат, связанная с данными.
